# Event Sourcing and CQRS
In every data model so far, data is **queried in the same form it is written** — JSON documents, table rows, graph vertices and edges. But in complex applications it can be hard to find a single representation satisfying every way the data needs to be queried and presented. In such situations it helps to **write data in one form and derive from it representations optimised for different types of read**. That idea appeared earlier as systems of record and derived data, and ETL is one example of such a derivation. Taken further: if we are going to derive one representation from another anyway, we can choose representations optimised separately for writing and for reading. So — how would you model your data if you wanted to optimise it **only for writing**, with efficient queries of no concern?

Probably the simplest, fastest, and most expressive way of writing data is an **event log**: every time you write, encode the data as a self-contained string (perhaps JSON) including a timestamp and append it to a sequence of events. Events in the log are **immutable** — never changed or deleted, only superseded by later appends — and an event can contain arbitrary properties.

The book's example is a conference management system, a genuinely complex domain: individual attendees register and pay by card; companies order seats in bulk, pay by invoice, and assign seats to people later; seats are reserved for speakers, sponsors, and volunteers; reservations get cancelled; the organiser may change capacity by moving to a different room. With all that going on, **simply calculating the number of available seats becomes a challenging query**. Under event sourcing, every state change is first stored as an event, and whenever an event is appended, several **materialized views** (also called **projections** or **read models**) are updated — one collecting the status of each booking, another computing charts for the organiser's dashboard, a third generating files for the badge printer.

Using events as the source of truth and expressing every state change as an event is **event sourcing**. Maintaining separate read-optimised representations derived from the write-optimised one is **command query responsibility segregation (CQRS)**. Both terms originated in the domain-driven design community, though similar ideas have been around a long time — for example in state machine replication.

## Key Takeaways
- **Commands become facts.** A request from a user is a **command** and must first be validated. Once executed and determined valid — there were enough available seats for the requested reservation — it becomes a fact and the corresponding event is added to the log. Consequently the event log should contain **only valid events**, and a consumer building a materialized view **is not allowed to reject an event**.
- **Name events in the past tense** ("the seats were booked"), because an event records that something happened. Even if the user later changes or cancels their reservation, it remains true that they formerly held a booking; the change or cancellation is a **separate event added later**.
- **Versus a star-schema fact table:** both are collections of past events. But fact-table rows all have the same set of columns, whereas event sourcing may have many event types each with different properties; and **a fact table is unordered, while in event sourcing order matters** — processing a booking and its cancellation in the wrong order would make no sense.
- **Advantages.** Events communicate *intent*: "the booking was cancelled" is easier to understand than "the `active` column on row 4001 of `bookings` was set to false, three rows were deleted from `seat_assignments`, and a refund row was inserted into `payments`" — those row modifications may still happen when a view processes the event, but the reason becomes clear. Views are **derived reproducibly**: you should always be able to delete a materialized view and recompute it by processing the same events in the same order with the same code, so a bug in view-maintenance code is fixed by deleting and recomputing, and is easier to find because you can rerun the code as often as you like. You can keep **multiple views** optimised for particular queries, in the same database or a different one, in any data model, denormalized for fast reads — even in memory only, if recomputing on restart is acceptable. Presenting existing information a new way just means building a new view from the existing log, and the system evolves by adding new event types or new properties (older events stay unmodified) or by chaining new behaviour off existing events (when an attendee cancels, offer their seat to the next person on the waiting list). An event written in error is reversed by a **subsequent deletion event**, which downstream views incorporate automatically — whereas in a database where you update and delete directly, a committed transaction is often difficult to reverse, so **event sourcing reduces the number of irreversible actions**. The log doubles as an **audit log**, valuable in regulated industries. And event logs typically handle **higher write throughput** than databases because of their sequential access pattern, absorbing bursts while downstream view maintainers catch up at their own pace.
- **Downsides.** **External information breaks determinism**: if an event contains a price in one currency that a view must convert, fetching the exchange rate from an external source at processing time would give a different result if the view were recomputed on another date — so you must either include the rate in the event itself or be able to query the *historical* rate at the event's timestamp, guaranteeing the same result for the same timestamp. **Immutability collides with GDPR**: users may request deletion of personal data. If the log is per-user you can delete that user's whole log, but not if it contains events relating to multiple users; you can store personal data outside the event or encrypt it with a key you can later destroy (**crypto-shredding**), but that makes recomputing derived state harder. And **reprocessing needs care where there are externally visible side effects** — you probably don't want to resend confirmation emails every time you rebuild a view.
- **The one hard requirement** is that the event storage system must guarantee that **all materialized views process events in exactly the same order as they appear in the log** — which, as the consensus chapter shows, is not always easy to achieve in a distributed system.

## Since the 1st Edition
Entirely new as a topic here. The 1st edition discussed event sourcing, immutable logs, and derived views — but in Chapter 11 (stream processing) and Chapter 12, as an *architectural* pattern arrived at after the machinery had been built. Presenting it in the **data modelling** chapter, alongside relational, document, and graph, reframes it as a modelling choice available from the start rather than a distributed-systems technique. CQRS is named explicitly, and crypto-shredding is new.
