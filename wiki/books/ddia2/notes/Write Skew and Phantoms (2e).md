# Write Skew and Phantoms
> Two doctors both check that two doctors are on call, and both go off call. Neither wrote to the same row, so no lock and no lost-update detector saves you.

## The Idea
An application manages doctors' on-call shifts. **The hospital must always have at least one doctor on call**, and doctors can give up a shift provided at least one colleague remains. Aaliyah and Bryce are the two on-call doctors; both feel unwell and **click the button to go off call at approximately the same time.**

Each transaction first checks that **two or more doctors are currently on call**; under snapshot isolation **both checks return 2**, so both proceed. Aaliyah takes herself off call, Bryce takes himself off call, **and now nobody is on call.**

**This anomaly is write skew.** It is **neither a dirty write nor a lost update, because the two transactions update two different objects** — Aaliyah's record and Bryce's record. It is less obvious that a conflict occurred, **but it is definitely a race condition**: had the transactions run one after another, the second doctor would have been prevented from going off call.

**Write skew is a generalization of the lost-update problem.** It can occur **if two transactions read the same objects and then update some of those objects** (possibly different ones). **In the special case of both updating the same object, you get a dirty write or lost update instead**, depending on timing.

## How It Works
**Your options are much more restricted than for lost updates:**
- **Atomic single-object operations don't help**, as multiple objects are involved.
- **Automatic lost-update detection doesn't help either.** **Write skew is not detected in PostgreSQL's repeatable read, MySQL/InnoDB's repeatable read, Oracle's serializable, or SQL Server's snapshot isolation level.** **Automatically preventing write skew requires true serializable isolation.**
- **Constraints usually can't express it.** To require at least one doctor on call you need **a constraint involving multiple objects**, and **most databases have no built-in support** — though you may be able to implement it with triggers or materialized views.
- **The second-best option is explicitly locking the rows the transaction depends on**, with `SELECT ... WHERE on_call = true AND shift_id = 1234 FOR UPDATE` before the update.

**More examples of write skew:**
- **Meeting room booking.** Check for conflicting bookings (same room, overlapping time), and if none, insert. **Snapshot isolation does not prevent another user concurrently inserting a conflicting meeting.**
- **Multiplayer game.** A lock prevents two players moving the same figure, **but doesn't prevent them moving two different figures onto the same square** or making another move violating the rules. A uniqueness constraint may cover some rules; otherwise you're vulnerable.
- **Claiming a username.** Two users try to create accounts with the same username at once. Checking then inserting **is not safe under snapshot isolation** — **but a uniqueness constraint is a simple solution here**, since the second transaction aborts on the constraint violation.
- **Preventing double-spending.** Insert a tentative spending item, list all items, check the sum is positive. **Two concurrent spending items can together push the balance negative without either transaction noticing.**

**Phantoms causing write skew.** All these follow the same pattern:
1. **A `SELECT` checks whether a requirement is satisfied** by searching for rows matching a condition.
2. **The application decides how to continue** based on that result.
3. **If it goes ahead, it makes a write** — and **the effect of that write changes the precondition of the decision in step 2.** Repeat the `SELECT` after committing and you'd get a different result.

(The steps may occur in another order — write first, then query, then decide whether to commit.)

**In the doctors case, the row modified in step 3 was one of the rows returned in step 1**, so `SELECT FOR UPDATE` in step 1 makes it safe. **The other four examples are different: they check for the *absence* of rows matching a condition, and the write *adds* a row matching that condition. If the query returns no rows, `SELECT FOR UPDATE` can't attach locks to anything.**

**This effect — where a write in one transaction changes the result of a search query in another — is called a phantom.** **Snapshot isolation avoids phantoms in read-only queries, but in read/write transactions phantoms lead to particularly tricky cases of write skew.** **The SQL generated by ORMs is also prone to write skew.**

## Trade-offs & Pitfalls
**Materializing conflicts.** If the problem is that there is no object to attach locks to, **can we artificially introduce a lock object?** For the meeting rooms: **create a table of time slots and rooms**, one row per room per 15-minute period, **populated for all combinations ahead of time** (say the next six months). A booking transaction then **`SELECT FOR UPDATE`s the rows for the desired room and period**, and after acquiring the locks checks for overlaps and inserts. **The extra table stores no booking information — it is purely a collection of locks.**

**This is called materializing conflicts, because it turns a phantom into a lock conflict on a concrete set of rows.** But **it can be hard and error-prone to figure out how to materialize conflicts, and it's ugly to let a concurrency control mechanism leak into the application data model.** **It should be considered a last resort if no alternative is possible; a serializable isolation level is preferable in most cases.**

## Examples & Systems
The on-call doctors, meeting room booking, multiplayer game, username claiming, and double-spending as the five write-skew scenarios; materializing conflicts as the last-resort workaround.
